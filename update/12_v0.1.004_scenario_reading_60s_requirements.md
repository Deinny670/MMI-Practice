# V0.1.004 Scenario Reading 60 Seconds Requirements

## Purpose

Scenario reading time is currently too short for realistic Melbourne-style station practice.

This change updates the fixed timing model so scenario reading is **60 seconds** instead of 30 seconds.

Scope is limited to the scenario reading duration and any metadata / tests that hard-code the old value. Preparation and answer timings stay unchanged.

## Current Behaviour

The station timing model starts with:

```text
Scenario reading: 30 seconds
```

This value appears in:

```text
04_timing_model_requirements.md
00_context_wave1_high_level_design.md
src/core.mjs timing constants
metadata.json timing.scenarioReadSeconds
related unit tests
```

Thirty seconds is not enough for many stations with longer scenarios.

## Target Behaviour

The station sequence must be:

```text
Scenario reading: 60 seconds

Q1 preparation: 15 seconds
Q1 answer: 60 seconds

Q2 preparation: 15 seconds
Q2 answer: 60 seconds

Q3 preparation: 15 seconds
Q3 answer: 60 seconds

Q4 preparation: 15 seconds
Q4 answer: 60 seconds

Station complete
```

Total station time becomes:

```text
60s + 4 * 75s = 6 minutes
```

During `scenario_reading`, the UI must still show:

```text
Scenario text
Phase label
Countdown in seconds
```

Recording must still start only at Q1 answer, not during scenario reading.

## Technical Approach

Update the shared timing source of truth used by the phase builder.

Likely files:

```text
src/core.mjs
test/core.test.mjs
04_timing_model_requirements.md is the base behaviour reference for implementers
```

Required changes:

```text
1. Change scenarioReadSeconds from 30 to 60 in the timing constants.
2. Ensure buildPhases / equivalent phase model uses the new duration.
3. Ensure metadata.timing.scenarioReadSeconds writes 60.
4. Update any tests that assert 30-second scenario reading or total duration derived from it.
```

Do not change:

```text
questionPrepSeconds = 15
answerSeconds = 60
questionCount = 4
audioSegments offsets relative to answer.webm
```

`audioSegments` remain relative to the continuous `answer.webm` that starts at Q1 answer. Extending scenario reading must not shift answer-segment offsets inside the recording file.

## Completion Criteria

1. Scenario reading phase lasts exactly 60 seconds in the timing model.
2. The practice UI countdown for scenario reading starts at 60.
3. Prep remains 15 seconds and each answer remains 60 seconds.
4. The phase order is unchanged: scenario reading, then four prep/answer pairs, then complete.
5. `metadata.json` writes `timing.scenarioReadSeconds: 60`.
6. Answer audio segment offsets in metadata still match the fixed answer windows inside `answer.webm`.
7. Existing recording still starts at Q1 answer and stops after Q4 answer.
8. Automated timing/phase tests pass with the new duration.

## Failure Handling

If the UI still shows a 30-second scenario countdown:

```text
1. Re-check the shared timing constant, not only display text.
2. Confirm the phase builder reads scenarioReadSeconds from that constant.
3. Re-test the first phase only before re-running the full station.
```

If metadata still writes 30:

```text
1. Update metadata construction to use the same timing constant.
2. Do not hard-code a second timing value.
```

If audio segment offsets become wrong after this change:

```text
1. Restore answer-relative segment calculation.
2. Remember scenario reading is outside answer.webm.
```

## Implementation Loop

1. Read this file and `04_timing_model_requirements.md`.
2. Change scenario reading duration to 60 seconds in the shared timing model.
3. Update metadata and tests that depend on the old value.
4. Run timing/phase tests and check every completion criterion.
5. Fix failures by returning to the relevant section.
6. Report exactly what changed and what was verified.
